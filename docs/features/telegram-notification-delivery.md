# Доставка Telegram-уведомлений

## Назначение

Документ фиксирует фактический контур доставки уведомлений, связанных с
консультациями, платежами и сроками дела.

## Создание уведомлений

`NotificationEngine` создаёт записи `Notification` по правилам из
`notification_rules.py` и шаблонам из `notification_templates.py`.

До появления отдельного поля fingerprint одинаковое событие дедуплицируется
по совокупности:

- `event_code`;
- `case_id`;
- `user_id`;
- метка получателя в `title`;
- полностью отрендеренный текст.

Повторная обработка одного и того же webhook, scheduler job или доменного
перехода не создаёт вторую идентичную запись. Изменение даты или текста создаёт
новое уведомление.

Эта проверка не заменяет уникальный constraint БД. Две строго одновременные
транзакции теоретически могут создать дубликат; для полной конкурентной
гарантии потребуется отдельный fingerprint и миграция.

## Доставка клиенту

`NotificationSender` выбирает только записи:

- `status = PENDING`;
- `is_sent = false`;
- `title = client`;
- с существующим `User`.

Telegram chat определяется только по сохранённому `User.telegram_id`.
Идентификатор получателя не берётся из callback, payload или текста события.

Последовательность доставки:

1. запись блокируется в текущей транзакции;
2. проверяется блокировка пользователя;
3. вызывается `Bot.send_message`;
4. только после успешного ответа выставляются `status = SENT` и
   `is_sent = true`;
5. внешний scheduler выполняет commit.

Если Bot не передан, sender возвращает `0` и не меняет записи.

## Ошибки доставки

- `TelegramRetryAfter` — обработка текущего batch прекращается, запись остаётся
  `PENDING` для повторной попытки;
- временная сеть или ошибка Telegram server — batch прекращается, запись
  остаётся `PENDING`;
- недоступный chat, запрет бота или некорректный адресат — запись получает
  `FAILED`;
- заблокированный в системе клиент — запись получает `FAILED` без вызова
  Telegram API.

## Scheduler

`AppScheduler` создаёт один Bot-клиент на весь цикл `run_forever`, если задан
реальный `BOT_TOKEN`, и передаёт его в `NotificationSender`.

В одном `run_once` выполняются:

1. создание напоминаний об открытых платежах;
2. освобождение истёкших consultation holds через `SlotService`;
3. контроль 30-дневного срока претензии;
4. отправка ожидающих клиентских уведомлений;
5. единый commit.

Bot session закрывается при остановке scheduler.

## Admin и lawyer recipients

Текущая модель `Notification` содержит `user_id`, но не содержит отдельные
`lawyer_id`, `admin_id` или универсальную ссылку на получателя.

Поэтому sender не помечает записи с `title = admin` или `title = lawyer` как
доставленные и не отправляет их по клиентскому `user_id`. Такие записи остаются
`PENDING` до появления безопасной recipient-модели или отдельного внутреннего
канала.

## События консультации

Клиентские события:

- `CONSULTATION_RESCHEDULED` — создаётся только после успешной атомарной замены
  booked-слота;
- `CONSULTATION_CANCELLED` — создаётся после успешной доменной отмены;
- неуспешный перенос или конфликтная отмена не создают уведомление;
- повторное событие с теми же данными переиспользует существующую запись.
