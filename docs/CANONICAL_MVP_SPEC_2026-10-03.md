# Digital Legal Concierge — каноническая спецификация MVP

**Статус:** FROZEN FOR CUSTOMER HANDOVER  
**Дата фиксации:** 2026-10-03  
**Версия продукта:** MVP по ДДУ 214-ФЗ  
**Правило релиза:** до передачи заказчику не добавлять новые продуктовые модули; исправлять только дефекты, блокеры запуска и несоответствия утверждённым М1/М2.

## 1. Источники требований

Единственными первичными продуктовыми источниками являются:

1. `docs/source_specs/Функциональная_спецификация_MVP.docx`;
2. `docs/source_specs/UX_UI_спецификация_Telegram_бот.docx`.

Этот документ является короткой технической фиксацией их обязательного объёма для разработки и приёмки.

### Иерархия при противоречии

1. Бизнес-границы, маршруты, обязательные шаги — функциональная спецификация.
2. Клиентские экраны, кнопки, callback, Back/Cancel/Error/Timeout — UX/UI-спецификация.
3. Допустимые переходы runtime — `CaseService` + `case_transition_policy.py`.
4. Миграции Alembic — единственный источник структуры production-БД.
5. Старые `WHAT_IS_READY_V*`, `START_SIMPLE_V*`, `HANDOVER_V*`, `FINAL_HANDOVER_V*` — исторические материалы и не являются источниками нового scope.

## 2. Граница MVP

MVP обслуживает только два маршрута:

- **М1 — стандартное взыскание неустойки по ДДУ**;
- **М2 — личная консультация**.

Третьих клиентских маршрутов нет. Один кейс не может одновременно находиться в М1 и М2. Перевод между М1 и М2 выполняется только допустимым доменным переходом и фиксируется в истории.

Клиентский кабинет — Telegram. Отдельный клиентский web-кабинет в MVP не требуется.

Система не выдаёт автоматическое юридическое заключение, не обещает результат суда и не заменяет решение юриста.

## 3. Роли

- **Клиент:** расчёт, документы, платежи, консультация, сообщения, просмотр статуса.
- **Администратор:** очередь дел, назначения, оплаты, консультации, контроль исключений.
- **Юрист:** проверка документов, решение по маршруту, сопровождение М1, консультации М2.
- **Система:** State Machine, уведомления, таймеры, audit, backup, provider/webhook processing.

## 4. Клиентская навигация

Канонические пункты Telegram:

- 🏠 Главная;
- 🧮 Рассчитать неустойку;
- 📁 Моё дело;
- 📄 Документы;
- 💬 Связаться с юристом.

Разделы показываются context-aware по состоянию дела. Возврат назад, отмена, timeout и техническая ошибка не должны уничтожать уже сохранённые данные.

## 5. Маршрут М1

Обязательная бизнес-последовательность:

`расчёт → решение продолжить → согласие ПД → документы → проверка юристом → договор → 30 000 ₽ → доверенность → претензия → 30 дней → суд → 70 000 ₽ → исполнительное производство → получение средств → 10% → закрытие`.

Ключевые правила:

- договор не открывается до решения юриста;
- доверенность не открывается до подтверждённого первого платежа;
- после претензии фиксируется дата и контролируется 30-дневный срок;
- исполнительный этап не открывается раньше предусмотренного судебного/платёжного перехода;
- финальное закрытие выполняется контролируемым доменным переходом.

## 6. Маршрут М2

Обязательная последовательность:

`вход в консультацию → описание ситуации → документы при наличии → выбор свободного времени → оплата/подтверждение по действующей конфигурации → консультация → решение юриста → М1 или закрытие`.

Ключевые правила:

- документы в М2 необязательны;
- слот резервируется безопасно и не считается окончательно подтверждённым до выполнения требуемого платёжного условия;
- перенос/отмена не должны терять вопрос и загруженные материалы;
- по итогам консультации юрист либо переводит кейс в М1, либо закрывает обращение.

## 7. State Machine

Канонический runtime-источник: `app/domain/statuses/case_statuses.py` и `app/domain/cases/case_transition_policy.py`.

Группы состояний:

- общий вход: `NEW`, `CALCULATOR_STARTED`, `CALCULATED`, `CLIENT_DECISION`;
- М1: документы → review → accepted/docs requested → contract → платежи → POA → claim → 30 days → court → enforcement → success fee → closed;
- М2: route → description → optional docs → slot → payment → booked → done → M1/closed;
- служебные terminal/recovery: `ERROR`, `ARCHIVED`.

Запрещено вводить второй независимый workflow engine или прямые произвольные записи `case.status`.

## 8. Backend и данные

Обязательный production-контур:

- FastAPI — HTTP/API и staff UI;
- aiogram — Telegram;
- PostgreSQL — основная БД;
- Alembic — схема и миграции;
- Redis — production FSM Telegram;
- persistent encrypted file storage — документы;
- scheduler — сроки, reminders, cleanup, backup jobs;
- YooKassa adapter + idempotent webhook ledger — реальные платежи.

SQLite и Memory FSM допустимы только для локальной разработки/тестов.

## 9. Документы

Первичный файл клиента является юридическим evidence-объектом дела.

Обязательные свойства MVP:

- привязка к точному `case_id`;
- версии и статусы проверки;
- encrypted-at-rest storage;
- controlled delivery/access;
- отсутствие path traversal/symlink bypass;
- исходный файл не должен незаметно подменяться производной версией.

OCR, Docling, OpenSearch, Presidio, OPA/OpenFGA и иные элементы Integration Master Plan не являются блокерами текущей передачи MVP и не должны расширять этот релиз.

## 10. Платежи

Production принимает подтверждение платежа только через реальный provider flow и webhook/API verification.

Обязательные свойства:

- provider event idempotency;
- replay/body mismatch detection;
- сверка суммы/валюты/metadata;
- бизнес-переход только после подтверждения;
- повтор webhook не создаёт повторный переход или проводку;
- fake provider запрещён production preflight.

## 11. Консультации

Календарь MVP — внутренний реестр доступных слотов юристов.

Обязательные свойства:

- выбор только свободного слота;
- hold/expiration;
- защита от двойного бронирования;
- перенос/отмена;
- напоминания;
- фиксация результата/неявки;
- решение М2 → М1 или закрытие.

Внешний Google Calendar не является обязательным условием MVP, если внутренний slot authority работает и проходит приёмку.

## 12. Уведомления

Уведомления — durable outbox, а не best-effort side effect бизнес-транзакции.

Минимум:

- payment reminders;
- consultation confirmation/reminders/change/outcome;
- document decisions;
- сообщения команды;
- SLA/claim deadline alerts;
- retry/backoff и явный FAILED для неустранимых ошибок.

## 13. Доступ и аудит

Обязательные production-инварианты:

- role-aware staff access;
- MFA для привилегированных операций;
- персональные сессии;
- audit trail критических действий;
- tamper-evident audit chain;
- ограниченные одноразовые grants для выдачи документов;
- секреты не хранятся в репозитории или логах.

## 14. Backup/restore

Перед go-live должны быть подтверждены:

- зашифрованный backup БД + файлов;
- верификация backup;
- restore в отдельный staging-контур;
- соответствие восстановленной схемы Alembic head.

## 15. Release acceptance

Релиз может называться **SOURCE ACCEPTED**, только если exact candidate проходит:

1. compile/architecture gate;
2. Alembic fresh + idempotency + schema parity;
3. полный SQLite test suite;
4. PostgreSQL migration/backup/restore drill;
5. container build/start health;
6. Telegram runtime contracts;
7. staff browser E2E;
8. locked dependency/test image.

Релиз может называться **CUSTOMER UAT READY**, только после staging deployment с production-like PostgreSQL/Redis/storage и реальными внешними credentials в тестовом/боевом контуре.

Релиз может называться **PRODUCTION ACCEPTED**, только после реального Telegram smoke, реального provider webhook/payment smoke, UAT М1/М2 и backup/restore evidence.

## 16. Freeze rule

До customer handover разрешены только:

- bugfix;
- security fix;
- test/CI repair;
- deployment/configuration repair;
- устранение расхождения с утверждёнными М1/М2;
- документация запуска/приёмки.

Любая новая возможность после этого — отдельная post-MVP change request.
