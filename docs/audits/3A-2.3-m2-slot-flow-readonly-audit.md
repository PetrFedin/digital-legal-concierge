# Этап 3A-2.3 — Telegram M2 Slot Flow

## Read-only аудит и план реализации

Базовый commit: `314c589d6f5c8b2a078ec3796d1bddba3dda5a7a`  
Ветка: `feat/lawyer-slot-confirmation`

## 1. Цель этапа

Строгая последовательность нового M2-flow:

```text
DESCRIPTION_PENDING
→ DOCUMENTS_OPTIONAL
→ SLOT_PENDING
→ SLOT_RESERVED
→ PAYMENT_PENDING
→ PAID_PENDING_CONFIRMATION
→ CONFIRMED / BOOKED
```

Этап 3A-2.3 должен реализовать только:

```text
SLOT_PENDING
→ выбор доступного слота
→ ConsultationService.reserve_pre_payment_slot()
→ SLOT_RESERVED
```

На этом этапе запрещено создавать Payment, вызывать `move_to_payment_pending()`, запускать payment webhook, подтверждать консультацию юристом или выполнять refund.

## 2. Текущие проблемы Telegram slot-flow

Существующий Telegram handler:

- использует legacy `ConsultationService.reserve_slot()`;
- может создать route-less Case через `ensure_booking_case()`;
- допускает прямой вызов callback до описания и документов;
- не проверяет `case.client_id == user.id`;
- не проверяет `case.route == M2`;
- не проверяет `Case.status == M2_SLOT_PENDING`;
- не выбирает строго одну активную Consultation;
- не проверяет `Consultation.case_id == Case.id`;
- не проверяет `Consultation.status == SLOT_PENDING`;
- не обрабатывает несколько активных Consultation;
- небезопасно парсит malformed `slot_id`;
- не проверяет активность Lawyer;
- не обрабатывает неизвестные legacy-статусы безопасно;
- сразу показывает оплату и возможность смены времени.

Legacy `reserve_slot()` не подходит новому flow, поскольку не использует state machine, сразу переводит Consultation в `PAYMENT_PENDING`, не синхронизирует Case и допускает замену ранее выбранного слота.

## 3. Правильный доменный контракт

Использовать только:

```python
ConsultationService.reserve_pre_payment_slot(...)
```

Ожидаемый результат:

| Объект | Значение |
|---|---|
| Consultation | `SLOT_RESERVED` |
| Case | `M2_PAYMENT_PENDING` |
| Case.next_action | `Перейдите к оплате консультации` |
| ConsultationSlot | `held` |
| AuditLog | `CONSULTATION_SLOT_RESERVED` |

Отдельного `CaseStatus.M2_SLOT_RESERVED` нет. Укрупнённый статус Case после резерва — `M2_PAYMENT_PENDING`, но Consultation должна оставаться в подробном статусе `SLOT_RESERVED` до отдельного следующего шага.

`move_to_payment_pending()` на этапе 3A-2.3 не вызывается.

## 4. Конкурентность и атомарность

`SlotService.hold_slot()` использует условный SQL UPDATE по `id` и `status='available'`. Для двух клиентов, выбирающих один Slot, это даёт атомарную защиту строки Slot на PostgreSQL.

Не полностью защищены:

- одна Consultation и два разных Slot одновременно;
- отсутствие блокировки строки Consultation;
- отсутствие DB-ограничения «один пользователь — один активный hold»;
- преобразование всех `IntegrityError` в контролируемую доменную ошибку.

`reserve_pre_payment_slot()` использует savepoint, поэтому изменения Slot, Consultation, Case и AuditLog откатываются вместе при ошибке внутри операции.

## 5. Hold и expiry

Фактическая длительность:

```text
SlotService.HOLD_MINUTES = 20
```

При этом в настройках и старом scheduler встречается 30 минут. Нужен единый источник истины.

Текущий `release_expired_holds()` очищает только ConsultationSlot и не синхронизирует:

- `Consultation.slot_id`;
- `Consultation.lawyer_id`;
- `Consultation.scheduled_at`;
- `Consultation.status`;
- `Case.status`;
- `Case.next_action`.

Это создаёт противоречивое состояние и может блокировать повторное назначение освободившегося Slot другой Consultation из-за уникального `Consultation.slot_id`.

Старый scheduler не является корректным механизмом освобождения нового hold: он не освобождает ConsultationSlot, не очищает `slot_id` и `lawyer_id`, не синхронизирует Case и не создаёт AuditLog.

## 6. Связь с payment-flow

Payment связан с Case, а текущий `consult_pay` не проверяет подробный Consultation.status и срок действия hold.

После `reserve_pre_payment_slot()` Case получает `M2_PAYMENT_PENDING`, поэтому `my_case.py` не должен автоматически открывать `consult_pay`, пока Consultation остаётся в `SLOT_RESERVED`.

На этапе 3A-2.3 после успешного резерва показывать только:

- дату и время;
- срок удержания;
- «Моё дело»;
- «Главная».

Не показывать:

- кнопку оплаты;
- кнопку выбора другого слота;
- автоматический переход в payment-flow.

## 11. Условия готовности

Этап готов, когда:

- новый Telegram M2-flow больше не вызывает legacy `reserve_slot()`;
- пропустить описание или документы невозможно;
- выбирается одна активная Consultation текущего клиента в `SLOT_PENDING`;
- Slot находится в будущем и принадлежит активному Lawyer;
- резерв создаётся через `reserve_pre_payment_slot()`;
- Slot, Consultation, Case и AuditLog фиксируются атомарно;
- повторный callback идемпотентен;
- expired hold освобождается согласованно;
- Payment не создаётся;
- кнопка оплаты не показывается;
- полный pytest и compileall проходят;
- deployment не выполняется в рамках этапа.
